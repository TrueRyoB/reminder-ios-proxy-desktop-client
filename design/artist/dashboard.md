## Gate 1b — 非冗長性検査(全ペア)

現行述語での判定:

| ペア | 判定 | 扱い |
|---|---|---|
| 今日 vs ダッシュボード | **今日 ⊆ ダッシュボード**(overdue∪dueToday ⊆ 現行4バケット) | **既定画面が他画面を包含 — 最優先提示(D1)** |
| フラグ付き vs ダッシュボード | **フラグ付き ⊆ ダッシュボード** | 同上(D1) |
| すべて vs 各画面 | **すべて ⊇ 全画面**(フィルタ無しなので自明) | 存在理由は C のみ。iOS にも「すべて」があるため、パリティ vs 非冗長性の衝突として D1 に併記 |
| 予定 vs ダッシュボード | 交差(将来の期日はダッシュボード外) | 独立性あり、保留不要 |
| 具体リスト vs 各 | 交差/独立 | 問題なし |

写像後(新述語)での再判定 — **包含が崩れて「ノイズ」に変わる**:

- 複数カード方式の採用後、「今日」「予定」「すべて」には儀式の**時点カード**(課題なし)が混ざる。新ダッシュボードは課題ありのみなので、包含関係は 今日 ⊄ ダッシュボード に変化するが、その差分は「ユーザーが見たくない時点カード」= ノイズ。
- したがって D1(冗長)と D2(述語再定義)は独立の判断: D1 は「画面を残すか」、D2 は「残す場合に課題ありフィルタを掛けるか」。
- 出所の衝突を明示: パリティ(C)は「iOS と同じ生集合」を要求し、製品価値(A: 参照面の資格規則)は「課題ありのみ」を要求する。**衝突はユーザ判断(D2)**。

## 承認結果(2026-08-01)

- **D1: スマートリストは「予定」「すべて」も含め全廃**(著者回答)。サイドバー = ダッシュボード+具体リストのみ。退避先としての生集合ビューが消える点は D2 の扱いと併せて具体リストが担う。
- **D2: pull 画面に課題ありフィルタを掛ける**(著者回答)。時点カードには通知でのみ会う。ただし時点カード・例外クラスの編集経路が必要なため、**具体リストのみ生集合**(唯一の raw ビュー)とする — 既定提案、異論あれば変更。検索はフィルタ側。
- **D3: クイック投函に格上げ**(著者回答)。3入口→ナビ直下インライン行。作成シートは廃止方向(次タスク提案の受け皿はクイック投函行の自動オープンで代替)。
- **D5: 並び替え入口はコメント解除で復活・具体リスト限定**(既定提案に異論なし、暫定)。
- **D4: 改訂**(著者指示 2026-08-01、逐語):「このキューの並び順こそ、今回のエンジニアリングの本質です。評価関数は、タスクの期限をすべて満たせることを前提に、地理的制約におけるバッチ化や認知切り替え負荷の最小化とします」「同じ系統の課題は、まとまった時間が確保できるのであれば、その時にこなすに越したことはない」「ぶっ続けでは疲れてしまうので、間に簡単な小規模のタスクが挟まれば息抜きになる」「就活系はスーツ着用・無地で静かな背景の制約があるため、関連性の有無にせよまとめて取り組んだ方が効率がよい」。これは先の回答「バッチングは初回外」を**上書き**する。順位付けは提示(UI)であり時間割当はしない、という境界で user-interaction の「スケジューラは設計しない」と整合させる。
  - 必要な新規入力: タスクサイズ/セッション宣言(環境・可処分時間、ダッシュボード上のUI)/エイジング(作成日から導出)。
  - Google カレンダー同期は「可処分時間の入力ポート」の将来の自動化として分離(v1 は手動宣言)。
- **D4追補: サイズは `priority` の転用で持つ**(著者確定 2026-08-01、逐語):「重要度を『所要時間』と見なすことで解決します。(リマインドに追加されている時点で、それの完遂義務は皆平等であるため)」。ローカル語彙の新設は不要になり、サイズも CloudKit フィールドだけから導出可能。写像(既定提案): 1(高)=大, 5(中)=中, 9(低)=小, 0(なし)=未設定→中扱い。iOS 側では ! マークの優先度表示として見える意味ずれを受容(flag=着手中と同型の転用)。編集シートのラベルは「所要時間(大/中/小)」へ変更。
- **D4'': 提示はキューの描画ではなく問い台帳に従う**(著者指示 2026-08-01:「そのデータ構造をユーザのUXに押し付けることは間違っている」「UIはユーザの問いに答える装置である」)。内部キュー(締切支配+編成)は推薦エンジンに退く。下記「問い台帳」参照。

## 問い台帳(Gate 1a 拡張 — 問い起点の逆算)

著者の前提(2026-08-01):「タスクを知らない状態から/それの実行に至るまで/それらの完遂に至るまで/何の問いが発生するか。それからダッシュボード設計は逆算できる」。
情報の不足差分は「ユーザの操作」(skip/DnD 等の行動シグナル)または「追加の入力負荷」(編集での整備)で解決する(著者の枠組み)。

**網羅性の規定**(著者要求「圏論的な網羅」の運用形):
(i) **全域性** — ライフサイクル各段階で発生する問いをすべて列挙し、答えの無い問いを残さない。
(ii) **対応の全射性** — すべての面はいずれかの問いを理由に存在する。問いなき面を作らない。
以後、画面の追加・変更はこの表への問いの追加・変更として行う(存在理由のハルシネーション防止)。

**ダッシュボードの形**: モード付き単一面。待機(Q2a+Q1a)⇄ 編成(Q2b+Q2c)⇄ 実行(Q3b+Q3c)。壁(全量リスト)はどのモードにも存在しない。

## 未決事項(著者登録 2026-08-01 → 同日、著者方針により全件解決・実装済み)

**解決(著者指示)**: U1/U2 = カスタムコレクション **upcoming** 方式 — 開始可能時間はフィールドでなく*コレクション所属*で表現。upcoming のカードは参照面に出ず、期日到来で行き先リストへ実カードを産む(繰り返しなら次回日付へ再装填=習慣、なければ完了)。開始(発火日)と終了(産むカードの締切=発火日+Nオフセット)は独立。U3/U4 = 属性は**タイトル内の `[キー]` メタタグ**で複数付与(iOS 可視・ストア消失に耐える。README コア価値3「メタタグを駆使して分類粒度を増やす」の回収)。キーの登録語彙と抽出ロジックはローカルストアで完結。実装: watch.rs `process_upcoming` / ProxyMeta(targetList・repeatDays・dueOffsetDays)/ ProxyStore.env_keys / 投函4入口目「＋あとで」/ 編集シートのタグチップ+キー登録。制約: リスト CRUD 未実装のため **upcoming リスト自体は iOS 側で一度作る**(存在しない間は「＋あとで」非表示)。
