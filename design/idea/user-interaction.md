# User Interaction

設計3層の最上段。人とリマインドの関係を定義する問題定義の層であり、画面の話はしない。

    user-interaction.md(なぜ・人とリマインドはどういう関係であるべきか)
      → expression.md(それをデスクトップでどう実現するか)
        → dashboard.md(具体的な画面)


## 1. リマインドは何のためにあるか

人がリマインダーに何かを預けるのは、**安心して忘れるため**。本質は短期記憶の負荷分散にある(旧草稿の核をそのまま採る)。

契約はこうだ:「これを預ける。正しい瞬間に、正しい形で返してくれ。」

ただし、預けているものは1種類ではない。よく見ると2つある。

- **課題** — 「やらなければならないこと」そのもの。返却は **pull 型**:
  人が「今、何をすべきか」を問い合わせたとき、信頼できる一覧として返ってくる。
- **時刻** — 「その瞬間に価値が集中する合図」。返却は **push 型**:
  システムの側から人の注意に割り込む。

この2つの関係は健全性の条件が正反対になっている。

- pull の健全性 = **参照面が信頼できること**。
  失敗モードは埋没と陳腐化 — 古いカードの壁ができると人は参照をやめる。
- push の健全性 = **割り込みが truly relevant であること**(コア価値2の文言そのもの)。
  失敗モードは空打ちの蓄積 → 通知盲 → 本当に必要だった1回が無視される。

2つは独立した関係であり、混ぜた瞬間に両方が壊れる。iOS 標準は「日時を設定したタスクは通知される」という形でこれを混同している。その結果、割り込み不要のタスクが通知を空打ちし(push の汚染)、一瞬の合図でしかないカードが完了されないままリストに残り続ける(pull の汚染)。


## 2. ガードレール:課題と通知の分離

本アプリのガードレールは **「やる課題と通知が分離されていること」**(著者確定。旧「iOS 側の意味を保つこと」を置き換える十分条件)。

- カードが課題を運んでいるかどうか、と、通知が何回飛ぶか、は**独立に決まる**。どちらも他方を含意しない。
- iOS 側の意味づけの枠(日時 ⇒ 通知、など)は、想定利用者の運用と衝突しない限り潰して良い(著者確定)。
- 1つの用事に複数のカードを割り当てることも、分離が保たれている限り許容される(著者確定)。


## 3. 軸

分離の原則をそのまま軸に立てる。カードは2つの**独立な属性**を持つ:

- **課題軸(あり / なし)** — このカードは「完了させるべき何か」を運んでいるか。
- **通知軸(0回 / 1回 / N回)** — システムは何回、人の注意に割り込むか。

どちらもタスクの**属性**であって状態ではない(flag=着手中のような状態とは別物)。ユーザーが UI で設定し、proxy ローカルに保持する — CloudKit に往復させない(著者確定)。

### 各軸が何を決めてしまうか

分類のための分類にしないため、各軸が確定させる事柄を先に固定する。

**課題軸が決めるもの:**

- **参照面に載る資格**。参照面 = アプリを開いたとき最初に表示される画面(ダッシュボード。位置で定義)。課題なしのカードは、人が「何をすべきか」を問い合わせる場所に出てはならない — 出た瞬間 pull が汚染される。
- **完了ライフサイクルの有無**。課題ありは完了まで生きる。課題なしは時点の通過で死ぬ。
- **締切の担い方**。課題ありのカードは締切を持ちうるが、締切は通知ではなく pull 側のデータであり、**通知を発火する担体には書かない**(§6 衝突A の解決)。実測(2026-08-01)により、時刻付き `due_date` は iOS で通知を発火し、終日(`all_day`)の `due_date` は発火しないと判明。したがって写像は「時刻付き=発火時刻(push 専用)/終日=締切(pull 専用)」となる(§5)。「締切が近い」で割り込みが欲しい場合だけ、時刻付き日時として正当に push 側へ書く。

**通知軸が決めるもの:**

- **push の全て**。0 = 絶対に割り込まない。1 = その時点で1回だけ。N = 計画された各時点で。
- 現3分類が持っていた良い性質 — 「型ごとに通知の是非が確定する」 — は、この軸に昇格して保存される。

### マトリクスと、現3分類の位置

|  | 通知0回 | 通知1回 | 通知N回 |
|---|---|---|---|
| **課題あり** | 型2 General task | *(空白セル)* 締切リマインド付きタスク | 型3 Long distant alarm |
| **課題なし** | — メモ。対象外 | 型1 Pure time-significant | *(空白セル)* 習慣リズム |

3分類はこの表の6セル中3つに名前を付けたものだった。空白だった2セルは実在する:

- **課題あり×通知1回** — 締切リマインド付きのタスク。iOS 標準で最も普通の使い方。日常すぎて見えなかった。
- **課題なし×通知N回** — 水を飲む、1時間ごとに立つ。型1 が「水を飲む」を挙げつつ short lifespan と書いていたのは、1回きりの合図と周期的反復を混同していた可能性が高い。

**課題なし×通知0回**だけは正しく空になる。それは単なるメモであり、リマインダーの守備範囲外。この空セルが正しく空になることは、2軸がリマインダーという領域を過不足なく張れている傍証でもある。

### なぜ3分類が上がってきたか

課題と通知がまだ分離されていなかったので、最も目立つ3つの組み合わせが「種類」として命名された、と読む。

lifespan が軸として失敗するのは、それが**結果側の量**だからだ。課題なしカードの寿命は発火時点まで、課題ありカードの寿命は完了まで — つまり lifespan は2軸の値から導かれる影であって、原因ではない。影で分類したから、投影が重なる2つ(1回きりの合図と周期反復)が型1に同居した。

なお、緊急度×重要度(Eisenhower)のような優先度軸は、参照面**内**の並び順の問題であって、カードの正体を決める軸ではない。それは dashboard 層の関心。さらに著者確定(2026-08-01):**重要度という軸はこのアプリに存在しない** — 「リマインドに追加されている時点で、それの完遂義務は皆平等であるため」。カードが持つ時間的性質は「量(所要時間)」と「位置(締切・発火時刻)」の2つだけであり、`priority` フィールドは所要時間の担体に転用される(expression 参照)。

### この軸も仮置きである(交換条件)

著者の明示に従い、この2軸にも囚われない。ただし乗り換えの条件だけ固定しておく:後継の分類は少なくとも

1. push の是非と回数を型ごとに確定させること
2. 参照面に載る資格を型ごとに確定させること

をやってのけなければならない。これより多くを、より少ない属性で決める分類が現れたら、乗り換える。


## 4. 各セルが人との間に結ぶ関係

セルごとに、その関係が UI に何を要求するかを書く。実現方式は expression の領域。

### 課題あり × 通知0回 — 純粋な課題(旧・型2)

割り込みは一切ない。**参照面が人との唯一の接点**になるため、参照面での actionability が全て。旧・型2 の条件群は「UI がどう補填するか」の要求としてここに接続される:

- **分解** — 提示されるカードは、拾った瞬間に手が動く粒度であるべき。粗いカードを割る手助けを UI が持つ。
- **ブロック** — 他のタスク待ちのカードは、参照面でそれと判るべき。
- **環境・場所** — 実行に場所や装備が要るもの(会議室の予約、制服)は、それが一目で判るべき。
- **目的** — 各課題は、元にある目的と切り離されずに見えるべき。
- **後続** — 完了は次の課題を生むべき。完了時の後続キャプチャは実装済みの足場がある(`gui/src/main.ts` の promptNextTask)。
- **バッチング** — 似た環境条件の課題は寄せて提示され、小さなタスクを合間に挟めるべき。

これらは全て pull 面の**提示の質**への要求であり、スケジューラや依存グラフの導入ではない(著者確定:作るのは UI のみ)。

(著者追記 2026-08-01)このセルの日時は「ない」のではなく**不明/柔軟**が正しい。したがってこのセルの契約には**漏れない保証**が含まれる — 構造的(専用コレクションに集めて視界から消えない)か、時間的(定期チェックのメタリマインド)か。メタリマインドは特定カードに紐づかず「参照面への回帰を促す」割り込みであり、カード単位の通知軸の外にあるシステムレベルの通知として区別する。方式は expression。なお、締切が**既知**だが割り込み不要のカード(衝突Aの主題)はこのセルの部分集合であり、締切保管用コレクションが受け持つ。

### 課題あり × 通知1回 — 締切つき課題(空白セルだったもの)

最も普通の使い方。pull と push の両方に属する:通知は「締切が来た」の1回で、課題は完了まで参照面に残る。通知を聞き逃しても課題は死なない — これが分離の恩恵の最小例。

### 課題あり × 通知N回 — 儀式的接近(旧・型3)

オンライン面接の 3h / 1h / 10min 前。各時点で要求される行為が違うため、これは「同じカードの再通知」ではなく**異なるメッセージの計画**である。行事の時刻で計画は終端する。

### 課題なし × 通知1回 — 純粋な時報(旧・型1)

会議前のひとこと。参照面には出ない(出ればノイズ)。発火したら役目を終えて死ぬ。死んだカードの処理はライフサイクル上のオープン問題(§6 衝突C)。

### 課題なし × 通知N回 — 習慣リズム(空白セルだったもの)

水を飲む、立ち上がる。完了概念がなく、終端もない。ここで通知軸の N の内部に区別があることに注意:**有限の計画**(あり×N は行事で終端する)と**周期の反復**(こちらは終わらない)。この区別の扱いは expression に渡す。


### 運用重心(著者承認 2026-08-01)

5段階のライフサイクル(発生/保管/着手/実行/完遂)への投資の優先順位は、習慣化×完遂を評価関数として **発生 > 着手 > 完遂 > 保管 > 実行**。

- **発生**: 失敗が無音(投函されなかったタスクは見えない)で、下流の全段階が静かに嘘になる。「預ける習慣」がデータの重力を作り、これが最強の定着要因。
- **着手**: タスクは実行中に失敗するのではなく、始まらないことで死ぬ。開いた瞬間の思考ゼロの即答が習慣の合図になる。
- **完遂**: 報酬でループを閉じ、後続キャプチャで発生へ還流させる。
- **保管**: 保証であって体験ではない。**禁欲則** — 保管系の画面を増やさない・飾らない。整理という偽の進捗を作らせない。
- **実行**: アプリは退く。通知以外の割り込みゼロ。最下位は放置ではなく「出しゃばらない」という設計判断。

この順位が決めるもの: スピード予算の配分(投函パス最優先)、待機画面の一等地(次の一手)、保管の禁欲、スコープ圧縮時の保護順(逆順に削り、投函と着手は最後まで守る)。例外規定: 着手→実行→完遂は1本の習慣ループであり、順位は投資の重み付けであってループの切断許可ではない。

## 5. 実装との接地(制約)

- `Reminder` の `due_date` は1つだけ(`core/src/reminders.rs:63`)。**1カードが原生的に表現できる時点は最大1つ**。通知N回は、複数カード(1用事複数カードは許容済み)か proxy ローカルの補助時刻でしか表現できない。方式の選択は expression。
- 軸の2属性は proxy ローカル(著者確定)。CloudKit スキーマには触れない。
- 現在の通知機構は due-reminder polling が1本だけで、通知の種類を持たない。つまり**通知軸はまだどこにも実装されていない**。「軸を読む通知」への要求として expression に渡す。細部:ポーラーはトレイ常駐でウィンドウを閉じても生きる(`gui/src-tauri/src/lib.rs:90`)が、間隔は5分固定(`watch.rs:14`)で「10分前」級のN回通知には粗く、通知済み集合はメモリ内(`watch.rs:18`)のため再起動で期限切れ全件が再通知される。
- 軸属性のローカル永続化の足場として `core/src/session_store.rs`(リストキャッシュの保存に既用)がある。
- (実測 2026-08-01)3件:**終日(`all_day`)の `due_date` は iOS で通知されない** — 通知を発火しない構造化された締切担体が既に存在する。ただしこの挙動は iOS の「今日の通知」設定に依存し、オンの環境では終日リマインダーが当日の設定時刻(既定 9:00)に通知されうる。著者判断(2026-08-01):この写像のまま進み、実用で不具合が目立てば修正する。**iOS のリスト表示は手動並び順(`ReminderIDs`)を尊重する**。**proxy の CRDT タイトル書き込みは iOS 側編集と共存する**。注意:現行ポーラー(`watch.rs`)は `all_day` を区別せず Windows 側で通知するため、写像を採る場合 proxy 側の修正が要る。
- スマートリストの述語がダッシュボードの真部分集合になっている現状(「今日」= overdue ∪ dueToday、「フラグ付き」= flagged に対し、ダッシュボードは overdue ∪ flagged ∪ dueToday ∪ priority==1)は、「参照面に何が載るべきか」の原理がないまま画面が別々の時期に足された症状。課題軸がその原理を与える。突き合わせの作業自体は expression / dashboard。
- 表現(コア価値3)の未使用資産のうち、flag は「着手中」、priority はダッシュボードのバケット判定に既に転用済み。コレクション名は手つかずだったが、§6 衝突A の解決で「締切保管用コレクション」としての実用価値の候補が立った。軸の2属性はこれらとは独立の、新しいローカル語彙になる。
- CloudKit の並び順はリスト単位(`ReminderIDs`)でしか持てず、`reorder()` は実装済みで iOS 側の表示順にも同期する(`core/src/reminders.rs:318`)。締切カードを1つの保管用コレクションに集めるのは、単一のソート済み締切列を iOS 可視にする実質唯一の方法。


## 6. コア価値との衝突(と著者判断による解決)

初稿では3つを未解決の衝突として提示した。いずれも著者判断(2026-08-01)で決着済み。経緯ごと残す。

### 衝突A:「通知0回」と iOS ネイティブ通知 → 解決(衝突自体が解消)

**当初の衝突**:課題あり×通知0回のカードに締切日時を持たせて CloudKit に書くと、iOS 側が独自に通知を飛ばす。(a) 漏れ通知を受容するか、(b) 日時をローカルに持って iOS 側の可視性を失うか — どちらも何かを失う、と提示した。

**著者の指摘**:この二択は「日付情報は `due_date` にしか持たせられない」という誤った前提から来ている。衝突の真因は、行動を始める合図と、締め切りの表示とが `due_date` に混在していたこと。

**解決の原則(確定)**:締切は通知ではなく pull 側のデータである。iOS から見えて、かつ通知を発火しない担体 — タイトル文字列・コレクション所属・手動並び順 — で持つ。**`due_date` は push 専用チャネルとし、締切を `due_date` に書かない。今後の設計で必ず分離する。** これによりフィールドの意味が一意化され、二択の両角が消える(iOS は通知しない、かつ締切は iOS からも見える)。

**具体候補(expression 送り)**:タスク名に日付を記した締切保管用コレクションを作り、更新のタイミングで自動ソートを走らせる。`reorder()` は実装済みで並び順は iOS にも同期する(§5)。→ その後の実測(§5)で、終日 `due_date` が「通知を発火しない構造化された締切担体」であると判明。第一候補は終日 `due_date` に更新され、保管コレクション+タイトル日付は補助(iOS 側に締切専用の単一ソート列が欲しい場合、時刻粒度の締切が要る場合)に降格。確定は expression。

**留保(致命的ではない)**:タイトル埋め込みの日付書式は iOS 側の手編集で壊れうるが、壊れても並び位置がずれるだけで目視で直せる。proxy 不在時はソートの更新が止まるが、表示は残るので劣化は緩やか。

### 衝突B:軸の設定コストとスピード → 解決の方向確定

**当初の衝突**:全カードの投函時に2属性を問えば、投函速度(コア価値1)が死ぬ。

**解決の方向(著者確定)**:属性ごとに投函の入口(ボタン)を分け、属性選択のコストを「どの入口から投函するか」の選択に折り込む。総クリック数は不変。副産物として、初稿で「既定値はどのセルが普通かの思想宣言になる」と書いた宣言が、ボタンの顔ぶれそのものとしてコストゼロで実現される。全セルに入口は不要 — 頻用セルに限り、稀な組み合わせは編集経由で足りる。顔ぶれの確定は expression。

### 衝突C:死んだカードの掃除 → 解消

**当初の懸念**:課題なしカードの発火後の自動完了・自動削除は共有データへの外向きの変更で、想定利用者の運用と衝突しないか要確認とした。

**著者判断**:問題ない。発火後カードの自動掃除は許容と確定。方式の設計は expression。

### 受容済みの緊張(衝突ではなく記録)

1用事複数カードは iOS 側のリストの見た目を汚すが、分離が保たれている限り許容と著者が明言済み。


## 7. expression.md への引き渡し

### 確定済みの入力条件(著者回答 2026-08-01)

- **通知N回は複数カード方式**。iOS 側でも鳴ることを要求する。帰結として、あり×N は実現上「課題カード1枚+時点カード(なし×1)N枚」の合成になる — セルは意図の分類、実現はカードの合成。発火済み時点カードは衝突Cの掃除に乗る。どのカード群が1つの儀式かを紐づけるローカル語彙は expression。
- **未分類カード(iOS 起票・既存ストック)の既定セル**:日時なし → あり×0(締切不明)、終日日時 → あり×0(締切既知)、時刻付き日時 → あり×1(実測による精緻化)。既定分類が CloudKit フィールドだけから導出できるため、**未分類カードにローカル属性は不要** — ローカル属性は例外(時報・習慣・儀式)の上書きだけ持てば足りる。既存ストックは分類作業なしで即、参照面に載る資格を得る。
- **投函ボタンの顔ぶれ**:あり×0 / あり×1 / あり×N の3つ。なし×1(時報)となし×N(習慣)は編集経由での投函 — この顔ぶれは「このアプリの普通は課題側」という宣言である。
- **型2条件群の初回スコープ**:目的・分解・環境/場所(+漏れない保証の機構、§4)。ブロックとバッチングは初回外。後続は実装済み。

### expression が決めること(ここでは決めない)

1. **締切保管用コレクションの設計** — タイトルの日付書式、自動ソートのトリガ、通常リストとの関係(移動か複製か。1用事複数カードは許容済み)(衝突A の解決を受けて)。
2. **あり×0 の漏れない保証の機構** — 専用コレクション(構造的)か、定期チェックのメタリマインド(時間的)か、併用か(§4 著者追記を受けて)。
3. **軸を読む通知** — polling 1本(5分固定・通知済み集合メモリ内、§5)から、通知軸(0 / 1 / N)を尊重する通知への再設計。
4. **参照面の資格規則の適用** — 課題ありのみを載せる。並び・バケット・提示の質(目的 / 分解 / 環境の補填)は expression → dashboard。
5. **課題なしカードの発火後ライフサイクル** — 自動掃除は許容済み(衝突C)。完了扱いか削除か、いつ走らせるかの方式設計。
6. **スマートリストとダッシュボードの述語の突き合わせ** — 課題軸を原理として。

この文書が保証すること:上のどの決定も、**課題と通知の分離を壊さない限り自由**である。
