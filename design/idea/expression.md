# Expression

user-interaction.md で定義した人とリマインドの関係を、この Windows デスクトップ proxy client で**どう実現するか**の設計論。画面の具体(配置・遷移・区画)は dashboard.md の領域、視覚仕様は `../stylesheet/` の領域。

**入力**(user-interaction.md §7 で確定済み):2軸(課題×通知)/通知N回=複数カード方式(iOS でも鳴る)/投函ボタン=課題系3セル/型2初回範囲=目的・分解・環境+漏れない保証/発火後の自動掃除は許容。

**接地**(同 §5、実測済み):時刻付き `due_date` は iOS で鳴り、終日は鳴らない。iOS は手動並び順(`ReminderIDs`)を尊重する。CRDT タイトル書き込みは iOS 編集と共存する。ポーラーは5分固定・通知済み集合はメモリ内。`session_store` がローカル永続化の足場。


## 1. 語彙の実現 — フィールド写像

原則:**通知を発火する担体に締切を書かない**(分離のフィールド版)。

| 意味 | 担体 | 由来 |
|---|---|---|
| 発火時刻(push) | 時刻付き `due_date` | iOS・proxy 双方が通知する(実測) |
| 締切(pull) | 終日 `due_date` | 通知を発火しない構造化フィールド(実測) |
| 着手中 | `flagged` | 既存の転用を維持 |
| 所要時間(サイズ) | `priority` | 著者確定(2026-08-01):重要度を所要時間と見なす — 「リマインドに追加されている時点で完遂義務は皆平等」なので重要度という意味は空いている。1=大, 5=中, 9=小, 0=未設定(中扱い)。iOS 側では優先度(!)表示に見える意味ずれを受容。逼迫度は (締切−現在)÷サイズ で導出 |
| テーマ | リスト所属 | iOS の従来意味を維持 |

この写像の最大の帰結:**既定分類もサイズも CloudKit フィールドだけから導出できる。**

- 時刻付き日時 → あり×1(締切リマインド付き課題)
- 終日日時 → あり×0(締切既知の課題)
- 日時なし → あり×0(締切不明の課題)

未分類問題は消滅する。ローカル属性が要るのは既定からの**例外**だけ:

- 例外クラスの宣言 — なし×1(時報)/なし×N(習慣)
- 儀式グループ — あり×N を構成するカード群の紐付け
- 型2語彙 — 目的・親子(分解)・環境タグ(§5)
- 通知済み集合の永続化(§3)

これらは `session_store` の隣にローカルストアを1つ増やして持つ(reminder id をキーに)。CloudKit へは往復させない(確定事項)。

**ストアの耐久性(著者確定 2026-08-01)**:カード本体は CloudKit に、意味だけがこのストアにある split-brain 構成のため、ストア消失=意味の全損(カードは無事なので静かに壊れる)。対策として、ストアは単一 JSON ファイルとし、起動時に `Documents` 配下へ**世代バックアップを自動で残す**(数世代・数KB)。単一 Windows 機前提の v1 はこれで足りる。2台目以降の同期は先送りとし、候補だけ記す:(a) iCloud for Windows の iCloud Drive フォルダに置く — API 不要でファイル同期を Apple クライアントに委譲、検証はフォルダ存在確認のみ、最有力。(b) 隠しリマインダーの `desc` に JSON を載せる — 検証済み API だけで書けるが iOS 側に奇妙なリストが見え、`desc` サイズ上限が未検証。(c) 自前 CloudKit コンテナ — Developer 契約と別認証が必要で、現行セッション認証からは使えない。

**要修正**:現行ポーラー(`watch.rs`)は `all_day` を区別せず Windows 側で通知する。写像の採用と同時に「終日はスキップ」へ改める。

### 締切保管用コレクションの扱い(衝突A 具体候補の更新)

タイトル日付+専用コレクション+自動ソート案は、実測により第一候補の座を終日 `due_date` に譲る。理由:パース不要(書式破損リスクが消える)、iOS 標準の「日時指定」スマートリストで締切列が可視、実装が写像の解釈だけで済む。

保管コレクション案は次のどちらかが立ったときの補助として温存する:(a) iOS 側に「締切だけの単一ソート列」が欲しい、(b) 時刻粒度の締切(17:00 締切だが鳴らさない)が要る。並び順の同期は実測検証済みなので、必要になれば追加コストは小さい。**v1 では見送り**。


## 2. 投函の実現

3つの入口(顔ぶれは確定済み)。いずれも「タイトル+最小限」で閉じ、総クリック数は現行の単一「+」と同等 — 入口の選択が属性の選択を兼ねる(衝突B の解決)。

- **やること**(あり×0。旧称: 課題):タイトルのみ必須。**鳴らない**。締切は任意 — 付ければ終日日時として書く。
- **リマインド**(あり×1。旧称: 締切つき):タイトル+時刻付き日時。**その時刻に鳴る**。
- **イベント**(あり×N。旧称: 儀式):タイトル+行事時刻+ラダー。**本番まで段階的に鳴る**。

(改称は Gate 2 フィードバック「課題にも締切を設けられるため、締切つきとの境界が謎」を受けたもの — 入口を分ける述語は締切の有無ではなく**通知の回数**なので、名称とヒントに「鳴る/鳴らない」を載せる。2026-08-01)ラダーは編集可能なテンプレ(既定:3時間前 / 1時間前 / 10分前)。投函1回で以下を一括生成し、ローカルの儀式グループで紐付ける:
  - 課題カード1枚(行事本体。時刻付き日時=行事時刻 → 行事時刻にも鳴る)
  - 時点カードN枚(なし×1。各時点の時刻付き日時。タイトルは「{行事}まで{Δ}」の自動生成)
  - 方式の根拠(著者確定 2026-08-01):各時点で**取るべき行動が異なる**ため、時点は「通知」でなく「文面(タイトル)を持つカード」でなければならない。CloudKit の Alarm レコードは文面を運べず代替にならない。時点カードの陳腐化(iOS 側で行事時刻だけ変更された場合)は既知のコストとして受容し、ポーリング時に儀式グループの再整合(課題カードの時刻変更を検知してラダーを再生成)で緩和する。

時報(なし×1)・習慣(なし×N)は編集経由での投函(頻度低と宣言済み):既定の入口で投函後、編集シートで例外クラスを付け替える。

投函先リストの選択は現行 create sheet の既定(現在ビュー優先)を踏襲する。


## 3. 軸を読む通知

現行1本のポーリングを、写像を読むよう再設計する。

1. **終日カードをスキップする** — 締切は鳴らさない(§1 要修正)。
2. **精度** — 5分ポーリングは維持しつつ、次のポーリングまでに発火する時刻付きカードへ精密タイマを張る。「10分前」が最大5分遅れる現状を解消する。
3. **通知済み集合の永続化** — `session_store` 系に保存し、再起動での期限切れ全件再通知を止める。
4. **発火後の掃除**(衝突C の適用) — なし×1(時報・儀式の時点カード)は発火後に自動**完了**にする。削除でなく完了:可逆で、iOS 側では完了済みに沈む。儀式グループは全時点の消化後も課題カード本体が完了まで残る。
5. **習慣**(なし×N) — カードを持たないローカル周期通知として最小実装する(タイトル+間隔+稼働時間帯をローカル定義。CloudKit レコードを消費しない)。v1 では設定を編集シート内の最小フォームに留め、重ければ次版へ送る。
6. **メタリマインド**(漏れない保証・時間側) — カードに紐づかないシステムレベルの定期通知。既定:週1回、「締切不明の課題が N 件」を参照面への回帰導線つきで。頻度・文言はローカル設定。


## 4. 参照面への供給

資格規則(user-interaction §3)の適用:参照面に載るのは**課題ありのカードのみ**。除外は例外クラス(時報・習慣)と儀式の時点カード。既定分類は全て課題ありなので、iOS 起票カードは何もしなくても載る。

参照面(および他の pull 画面)へ供給する材料:

- 締切(終日日時、なければ「不明」)/発火時刻(時刻付き日時)/着手中(flag)/priority/目的/環境タグ/親子関係/儀式グループ

並び・バケットへの合成規則は dashboard.md。

**漏れない保証(構造側)**:「締切不明」の課題は参照面に常設の区画として持つ(配置・形は dashboard.md)。時間側の保証は §3-6 のメタリマインド。両輪で運用する。


## 5. 型2語彙の実現(目的・分解・環境)

いずれもローカルストアに持つ。`desc`(iOS 可視)は汚さない — iOS 側の見え方を変えず、書式破損の再発も避ける。

- **目的**:カードに1行の目的テキスト(または他カードへの参照)。後続キャプチャ(promptNextTask、実装済み)時に自動継承し、完了→次タスクの連鎖で目的が途切れないようにする。
- **分解**:カードを子カードに割る操作。子は同リストに実カードとして生成(iOS でも見える)し、親子はローカルで**1段だけ**紐付ける。親は「全子完了で完了を促す」に留め、依存グラフにはしない(user-interaction の禁止事項)。目的は子へ継承。
- **環境/場所**:ローカルの自由タグ(少数語彙を想定:家 / 会社 / 外出 / PC など)。v1 では付与と表示まで。タグによる寄せ集め提示(バッチング)は初回外(確定済み)だが、この語彙がその下地になる。


## 5.5 開始可能時間と属性(U1〜U4 の解決、著者確定 2026-08-01)

- **upcoming 方式(U1/U2)**: 「upcoming」という名のコレクションを待機庫とする。開始可能時間はフィールドではなく*コレクション所属*で表現され、upcoming のカードは参照面の資格を持たない(未到達の課題は見えない)。期日(終日=鳴らない)到来で、proxy が行き先リストへ実カードを産む。繰り返し(N日)があれば自分を次回へ再装填 — **習慣はこのループ**。産むカードの締切は発火日+オフセット(独立設定、未設定なら締切不明)。upcoming リスト自体はリスト CRUD 未実装のため iOS 側で一度作る。
- **メタタグ(U3/U4)**: 属性はタイトル内の `[キー]` として複数付与できる。担体がタイトルなので iOS からも見え、ローカルストア消失にも耐える(README コア価値3の「メタタグ」構想の回収)。キーの登録語彙(家/PC/外出/スーツ+自由追加)はローカルストア、抽出はタイトルのパース。編成スコアの環境一致はタグ集合∋宣言環境で判定。表示時はタグを剥がしてバッジ化する。ProxyMeta.env は廃止(後方互換のため残置)。

## 6. 参照系画面の述語の整理原則

全ての pull 画面(参照面・スマートリスト・検索)の述語は、§1 の写像+§5 の語彙から導出し、**画面間の集合関係を明示して設計する**。現状の「別々の時期に別々の基準で足され、集合として突き合わされていない」状態の再発防止。

- 既存スマートリスト(「今日」「日時指定」等)は写像後の意味 — 発火時刻と締切が同じ画面に混在しうる — を踏まえて述語を再定義する。
- 参照面の述語(課題あり)と各スマートリストの包含関係は dashboard.md に表で残す。


## 7. コア価値との整合(点検)

- **スピード**:入口3ボタンで投函クリック数は不変。写像による既定分類で、既存ストックの移行作業もゼロ。
- **可用性**:通知は複数カード+時刻付き日時なので iOS 側でも鳴る(proxy 不在時も欠けない)。締切は終日日時で iOS からも可視。例外は習慣のローカル周期通知とメタリマインドで、これらは proxy 稼働時のみ — トレイ常駐(実装済み)が前提。
- **表現**:未使用資産のうち flag・priority は転用を維持。**コレクション名は v1 でも未使用のまま**(保管コレクション見送りの帰結。正直に記録)。
- **ガードレール(課題と通知の分離)**:通知の由来は push 担体(時刻付き日時・ローカル周期)のみ、参照面の掲載資格は課題軸のみ。分離が構造として保たれる。
